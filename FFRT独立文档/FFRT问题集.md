## 一、队列过载与排查（实战问答）

**Q1. TrafficRecord 日志里的 subcnt / doncnt 是什么意思？**

队列的**累计提交数 / 累计完成数**（doncnt 是源码原始拼写）。与之相对的 in/out 是默认 6s 观测窗口内的增量。`subcnt − doncnt` = 当前在途任务数（排队 + 待执行 + 执行中 + 阻塞中），防溢出同减不影响差值。→ 细节篇 §7.3/§7.4

**Q2. subcnt 比 doncnt 大 2 万，说明什么？**

约 2 万任务在途。结合 in/out 趋势分三种画像：in>out 且差值扩大 → 生产过载；in/out 停滞、差值不动 → 消费卡死（查 dump 的 blocked 分组）；差值稳定且无告警 → 可能是延时任务或合法深流水线。→ §7.4 诊断三分法

**Q3. 过载会导致队列执行卡顿吗？**

会，但分开看：**排队延迟是必然的**（第 N 个任务等 ≈ N × 单任务耗时）；执行吞吐的次生影响有限（队列锁竞争、日志开销、内存局部性）。且常见因果倒置——过载往往是队头卡死的**结果**。→ §7.4

**Q4. 队列积压会拖垮队列外的普通任务吗？**

基本不会。积压躺在队列自己的 `whenMap_` 里，只有达到并发上限的任务才进调度器；但同 QoS 的普通任务会和已派发的队列任务竞争全局队列。→ §7.4

**Q5. 提交任务时 kmsg 会有什么打印？**

**正常情况下什么都没有。** FFRT 日志走 hilog（非 OHOS 走 stdout）、生命周期走 HiTrace、统计在进程内存里。提交触发的内核交互（futex、clone、QoS/RTG ioctl）成功时内核侧均静默；kmsg 出现 FFRT 内容只有异常场景（内核驱动报错、崩溃、OOM、hung task）。→ §8.8 日志通道表

**Q6. 并发队列不设 max_concurrency 会怎样？**

**默认并发度为 1，按串行跑**（`CreateConcurrentQueue` 中 `<=0 ? 1`）。以为建了并发队列实际是串行，是常见的"没提速"根因。→ §7.1

## 二、机制理解（学习自测）

**Q7. 一个任务从提交到完成经历什么？**

submit → 依赖管理器建对象（闭包与任务同块内存）→ ins/outs 映射成版本链依赖图 → 依赖满足则 Ready → 按 QoS 入全局 FIFO 队列 → 唤醒 Worker → 协程中执行用户函数 → onTaskDone 解依赖、唤醒下游。→ 骨架篇主链路九步

**Q8. 提交顺序会影响依赖正确性吗？**

不会。先提交生产者产生 RAW（消费者等生产）；先提交消费者产生 WAR（写者等读者读完）——版本链天然编码两种顺序。已通过冒烟测试实证。→ §2.7 走例

**Q9. 为什么 handle 不能做输出依赖？**

handle 是任务的"完成事件"，只能被等待不能被生产；submit_h 内部会把 handle 追加为该任务的输出签名。→ §1.3

**Q10. 任务在协程里 sleep 时，Worker 在干什么？**

跑别的任务。sleep 走 CoWait 让出协程，Worker 立即取下一个任务；定时到期再把睡眠任务唤醒重新入队。冒烟实证：8 个各睡 50ms 的任务总耗时 50ms 而非 400ms。→ §5.4/§6.2

**Q11. per-QoS 到底隔离了哪些东西？**

四样：运行队列、Worker 线程池、全局调度锁、监控计数。低 QoS 洪泛不会拖慢高 QoS 的入队与取队。→ §4.1

**Q12. 协程模式下任务 done 后为什么不立即解依赖？**

onTaskDone 会唤醒消费者，消费者可能立刻复用这块 slab 内存，而当前协程的收尾代码还要访问 task->coRoutine——提前解依赖就是 use-after-free。所以置 isTaskDone 标志，延迟到协程收尾统一处理。→ §3.4

**Q13. 任务超时 watchdog 会取消任务吗？**

**只检测不取消**。超时后任务继续执行，回调用于业务侧降级/记录；且回调在 DelayedWorker 线程上跑，不过调度器。→ §8.3

**Q14. dump/bbox 怎么知道哪些任务还活着？**

slab 分配器天然跟踪未释放的任务对象（`GetUnfreedMem`），普查依赖这个底座；bbox 写快照时任务 FreeMem 前自旋冻结，防止内存被复用污染快照。→ §8.5/§8.6

## 三、观察与工具

**Q15. 想看单个任务的完整生命周期，用什么？**

开 HiTrace 的 FFRT tag（bit 13），看 P（提交）/R（就绪）/B（阻塞，含 10 种原因标签）/F（完成）标记；跨 Worker 打散的 trace 用 `ffrt_trace_recover.py` 复原成逻辑任务视角，`ffrt_trace_process.py` 出统计报表。→ §8.1/§8.10

**Q16. ffrt_dump 四条命令分别输出什么？**

`DUMP_INFO_ALL` 全量快照（Worker 状态、任务普查、暂停协程栈回溯、超时记录、队列流量）；`DUMP_TASK_STATISTIC_INFO` 计数器汇总；`DUMP_START_STAT/STOP_STAT` 开关任务明细环形记录（任务级 profiler 窗口）。→ §8.5

**Q17. bbox 什么时候触发？输出什么？**

SIGABRT/BUS/FPE/ILL/STKFLT/SYS/TRAP/INT/KILL 任一信号，且 FFRT 曾被使用、只保存一次。克隆子进程写快照（任务计数 + 不变量校验 + 任务普查 + 协程栈），最多等 2 秒，之后把信号重发给默认处理让崩溃照常走。→ §8.6
